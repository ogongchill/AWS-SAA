# Versioning

>*Versioning = “데이터를 덮어쓰지 않고 버전별로 누적 보관한다.”*

|항목|설명|
|---|---|
|목적|**객체 변경 및 삭제 이력을 모두 보관**|
|동작 방식|수정/삭제 시 **새 버전이 생성되고**, 기존 버전은 그대로 유지|
|장점|잘못 덮어쓰기/삭제해도 **이전 버전 복구 가능**|
|특징|버전 ID 단위로 객체 존재 → 삭제마저도 “삭제 마커”가 생성될 뿐, 실제 데이터는 남아 있음|
|전제|**S3 Object Lock을 사용하려면 Versioning이 반드시 활성화되어 있어야 함**|

# Legal Hold

> *Legal Hold = “지정 해제 권한자가 풀기 전까지 절대 삭제/수정 불가능한 무기한 잠금.”*

| 항목        | 설명                                         |
| --------- | ------------------------------------------ |
| 목적        | 객체가 **삭제되거나 덮어씌워지는 것을 아예 막기**              |
| 보존 기간     | **기한 없음 (무기한 유지)** → 해제할 때까지 불변            |
| 누가 해제 가능? | **`s3:PutObjectLegalHold` 권한이 있는 사용자만** 가능 |
| 특징        | **WORM(Write Once Read Many)** 정책 구현 가능    |
| 활용 예      | 회사가 “변경 금지” 기간을 유동적으로 관리해야 할 때 최적          |

# Amazon S3 Transfer Acceleration

>***전 세계 어디서든 S3 버킷으로 데이터를 더 빠르게 업로드/다운로드**할 수 있도록 해주는 기능*

사용자는 가까운 **AWS 엣지 로케이션(CloudFront Edge)** 으로 접속하고,  
AWS 내부 고속 네트워크를 통해 **S3 버킷 위치까지 빠르게 전달**되는 구조.

| 상황                                 | 의미                            |
| ---------------------------------- | ----------------------------- |
| **사용자가 S3 버킷 리전과 지리적으로 멀리 떨어져 있음** | 거리로 인해 전송 속도가 느릴 때 가속 효과 큼    |
| **대용량 파일 업/다운로드가 잦음**              | 데이터 전송 시간 단축 가능               |
| **전 세계 분산 사용자 환경**                 | 예: 글로벌 서비스, 게임 런처, 미디어 업로드 포털 |
|                                    |                               |
### 작동 방식

1. 사용자가 `bucketname.s3-accelerate.amazonaws.com` 으로 업로드 요청
2. 요청은 **가장 가까운 CloudFront Edge Location** 으로 전달
3. 엣지 로케이션 → AWS 전용 백본 네트워크 → S3 버킷으로 고속 전송

```mermaid

    C --> D[S3 버킷 데이터 전송]
```

# Glacier vs IA
### 🔹 **S3 Standard-IA / One Zone-IA**  
>**“자주 보진 않는데, 필요할 땐 바로(ms 단위) 꺼내야 하는 데이터”**
- Standard랑 똑같이 **ms 단위로 바로 읽기 가능**
- 대신 **저장비용은 싸고, 읽을 때(조회량 기준) 요금이 붙음**
- **최소 보관 기간 30일** (그 전에 삭제하면 early deletion fee)

### 🔹 **S3 Glacier 계열** (아카이브용)
> **“거의 안 본다. 꺼내는 것도 분~시간 기다려도 된다. 대신 존나 싸야 한다.”**
- 스토리지 요금 **가장 싸다**
- 복구 요청 자체에도 비용 + 전송 비용 + 대기 시간     
- “백업 / 규제 준수 / 감사용 기록” 같은 것에 최적

## 판단 기준

### ✅ Standard-IA / One Zone-IA 를 쓸 때

- ✅ **언제라도 바로(실시간) 읽어야 할 수 있고**
- ✅ **실제로는 자주 안 읽는 데이터**일 때

```
- 사용자 업로드 파일 중 “최근 30일은 자주 보지만, 그 이후엔 가끔 보는” 이미지, 첨부 파일
- 로그/리포트 중에서 가끔 운영자가 바로 열어봐야 하는 것
- 주문/거래 내역 중 “과거 내역도 화면에서 즉시 조회 가능해야 하는” 경우
```

시험에서 나오는 키워드:

- “**infrequently accessed but must be immediately available**”
- “**millisecond access is still required**”  
    👉 **Standard-IA / One Zone-IA**

### ✅ Glacier(아카이브) 계열로 보내야 할 때
- ✅ **읽을 일이 거의 없다**
- ✅ 읽는다 해도 **몇 분~몇 시간 기다려도 상관 없다**
- ✅ **장기 보관이 목적**이다 (규제, 감사, 백업)

```
- 1년치 액세스 로그, 7년 보관해야 하는 회계/세금 관련 데이터
- 백업 스냅샷, DR용 백업
- “규정상 5년 보관해야 하지만 거의 안 여는 파일”
```

시험에서 나오는 키워드:

- “**Archive**”
    
- “**cold data**”
    
- “**long-term retention**”
    
- “**hours to retrieve is acceptable**”  
    👉 **Glacier (Flexible / Deep Archive)**

## 3. 라이프사이클 전환 패턴 예시

실무/시험 둘 다에서 자주 나오는 패턴:

### 패턴 1 – 일반적인 웹 서비스 로그/파일

`0~30일: S3 Standard (자주 조회됨) 30~90일: Standard-IA (가끔 조회됨) 90일 이후: Glacier Flexible Retrieval or Deep Archive (거의 안 봄, 보관만)`

### 패턴 2 – 규제/감사용 데이터 (거의 조회 안함)

`0~30일: S3 Standard (막 적재되는 중) 30일 이후: 바로 Glacier / Glacier Deep Archive`

### 패턴 3 – 사용자 파일(옛날 사진, 업로드 자료 등)

`0~60일: S3 Standard 60~365일: Standard-IA (예전에 올린 거지만 클릭하면 바로 떠야 함) 1년 이후: Glacier Instant Retrieval (아주 가끔 조회) 혹은 3년 이후: Deep Archive`
## 4. IA vs Glacier를 결정하는 “질문 3개”

이 3개만 묻고 답하면 됨:

1. **“사용자가/시스템이 이 데이터를 바로(ms) 읽어야 하냐?”**
    - YES → **Standard / Standard-IA**
    - NO, 몇 분~몇 시간 괜찮다 → **Glacier 계열**
    - 
2. **“이 데이터를 실제로 얼마나 자주 읽냐?”**
    - 가끔 읽음 → IA
    - 진짜 거의 안 읽음 → Glacier
        
3. **“목적이 조회냐? 보관이냐?”**
    
    - 조회/검색/리포트용 → IA 또는 Standard
        
    - 보관(규제, 백업, DR) → Glacier
